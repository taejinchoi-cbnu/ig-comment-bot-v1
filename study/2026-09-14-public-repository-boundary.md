# 공개 저장소로 바꾸면서 문서를 지운 것은 프로젝트의 근거를 버린 게 아니었다

> 2026-09-14 · Phase 1 완료 뒤 공개 전환 준비
>
> 파이프라인은 실계정에서 검증됐고, 이력은 포트폴리오로 공개할 수 있는 상태가 됐습니다.
> 그런데 공개할 코드와 공개하면 안 되는 운영 기록이 같은 저장소에 있었습니다.

## P — Problem

`docs/`에는 설계 근거뿐 아니라 실계정 username, 실제 webhook·배포를 확인한 로그, 운영 중에만
의미 있는 메모가 함께 있었습니다. `ops/`는 이미 Git에서 제외했지만, 문서는 추적 대상이어서
공개 저장소로 전환하면 지인 계정과 운영 환경의 흔적까지 같이 노출되는 상태였습니다.

예시 배포 환경 파일에도 실제 AWS 계정 ID가 들어 있었습니다. 시크릿은 아니지만, 공개 예시가
특정 운영 계정을 가리킬 이유가 없습니다.

반대로 문서를 통째로 삭제하면 Phase 1에서 검증한 Meta 제약, 설계 선택, 트러블슈팅 근거가
사라집니다. 공개 범위를 줄이는 일과 프로젝트의 판단 근거를 버리는 일을 같은 것으로 보면
안 됐습니다.

## A — Analysis

공개 독자가 필요한 정보와 운영자가 필요한 정보를 나눴습니다.

| 독자 | 필요한 것 | 공개하면 안 되는 것 |
|---|---|---|
| GitHub 방문자 | 서비스 목적, 실제로 동작한 백엔드 범위, 아키텍처, 실행 방법, 라이선스 | 실계정 username·이벤트 로그·운영 절차의 식별 가능한 맥락 |
| 운영자 | Meta 설정·실계정 검증 기록·복구 절차·상세 설계 근거 | GitHub에 자동 배포되는 공개 사본 |

문서를 안전하게 만들기 위해 모든 문장을 익명화하는 방법도 있었지만, 약 4천 줄의 설계·로그·
아카이브를 지속적으로 검수해야 했습니다. 한 번 빠뜨리면 공개 전환의 목적이 사라지고, 이후
운영 기록을 쓸 때마다 같은 검수가 반복됩니다.

따라서 공개 저장소에는 안전한 요약 README만 두고, 식별 가능한 운영 문서는 로컬 `docs/`에
남기는 경계가 더 작고 검증하기 쉬웠습니다. 이는 문서를 포기한 것이 아니라 **독자별로
문서의 책임을 분리한 것**입니다.

## A — Action

1. `docs/`를 Git 추적에서 제외하고 ignore 규칙에 넣었습니다. 로컬 작업 공간에는 남겨
   구현·운영의 근거 문서로 계속 사용합니다.
2. 공개 README를 다시 써서 서비스가 무엇을 하는지, Phase 1이 어디까지 실동작하는지,
   webhook과 워커의 핵심 불변식, 로컬 실행 방법을 문서 링크 없이도 이해할 수 있게 했습니다.
3. `ops.example/deploy.env.example`의 실제 AWS 계정 ID를 `ACCOUNT_ID` 자리표시자로 바꿨습니다.
   실제 자격증명은 아니어도 공개 예시는 특정 계정을 드러내지 않습니다.
4. `CC BY-NC 4.0` 라이선스를 추가하고 패키지 메타데이터에도 같은 라이선스를 표시했습니다.
   지인 대상·비상업 프로젝트라는 제품 범위와 공개 재사용 조건을 일치시켰습니다.

**안 만든 것**: 공개용 문서를 별도 사이트나 두 번째 저장소로 옮기지 않았습니다. 지금 필요한
공개 정보는 README 하나로 충분하고, 문서 배포 경로를 하나 더 만들면 동기화 실패 지점만
늘어납니다.

## R — Result

공개 저장소의 최신 트리에서 운영 문서는 빠지고 최상위 진입점은 README, study 기록, 라이선스로
줄었습니다. `docs/`의 운영·실계정 문서는 로컬에서 계속 참조합니다. 다만 문서를 삭제한 커밋
이전의 Git 이력까지 지워진 것은 아니므로, 공개 전에는 이력과 원격 접근 범위를 별도로 점검해야
합니다.

| 변경 | 결과 |
|---|---|
| `docs/` ignore + 추적 해제 | 새 공개 커밋에 운영 문서가 자동으로 들어가지 않습니다. |
| 공개 README | 문서 폴더가 없어도 현재 구현 범위와 아키텍처를 설명합니다. |
| 예시 ID 마스킹 | 공개 설정 예시가 실제 AWS 계정을 가리키지 않습니다. |
| CC BY-NC 4.0 | 비상업 재사용 조건이 저장소에 명시됩니다. |

이 전환은 과거 커밋에 이미 남아 있을 수 있는 값을 지우는 작업은 아닙니다. 공개 전에는 Git
이력 전체와 원격 저장소의 접근 범위를 별도로 점검해야 합니다. ignore는 앞으로의 실수를
줄이는 장치이지 과거 공개의 삭제 도구가 아닙니다.

## 배운 것

### 1. 공개 가능한 코드와 공개 가능한 운영 기록의 경계는 다르다

코드에 시크릿이 없더라도, 실계정 이름·실전 로그·인프라 식별자는 맥락과 결합될 수 있습니다.
"시크릿이 아니니 공개해도 된다"가 아니라, **이 정보가 공개 독자의 이해에 꼭 필요한가**를
먼저 물어야 했습니다.

### 2. 공개 문서는 운영 문서의 축약본이 아니라 다른 제품이다

운영 문서는 다음 장애를 빨리 고치기 위해 상세해야 합니다. 공개 README는 방문자가 프로젝트의
의도와 기술적 깊이를 짧게 판단할 수 있어야 합니다. 한 문서가 두 역할을 하면 상세함과 안전성
중 하나를 잃습니다.

## 면접용 30초 요약

> 실계정으로 검증한 Instagram 자동 DM 프로젝트를 공개 저장소로 바꾸려다, 코드보다 문서가
> 더 큰 개인정보 노출 지점이라는 걸 발견했습니다. 설계 문서에 실계정 username과 운영 로그가
> 섞여 있었기 때문입니다. 전부 익명화하는 대신 운영 문서는 로컬 전용으로 분리하고, 공개
> 저장소에는 독자가 필요한 아키텍처·현재 상태·실행 방법만 담은 README를 새로 만들었습니다.
> 예시 파일의 AWS 계정 ID도 플레이스홀더로 바꾸고 CC BY-NC 라이선스를 추가했습니다. 배운
> 점은 공개 문서와 운영 문서는 같은 내용을 짧게·길게 쓰는 관계가 아니라, 독자와 보안 경계가
> 다른 별도 산출물이라는 것입니다.
