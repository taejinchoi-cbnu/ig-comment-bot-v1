# 단위 테스트가 놓친 인증 주입 오류를 HTTP 테스트로 찾았습니다

> 2026-10-05 · Jest·Vitest 이관과 인증 회귀 검증
>
> 테스트 러너를 바꾸고 커버리지를 측정하는 작업에서, 실제 Nest 앱의 로그인 확인 요청이
> 500을 반환하는 기존 오류를 발견했습니다. 전체 검증이 통과한 뒤 결과를 기록했습니다.

## P — Problem

기존 Node 내장 테스트는 webhook 정규화, 본문 비저장, 계정 격리, 멱등성, 발송 재시도와
OAuth state·로그인 자격을 검증했습니다. 하지만 직접 객체를 만들어 호출하는 테스트만으로는
Nest가 구성한 의존성 그래프와 HTTP 쿠키·리다이렉트 동작을 확인하기 어려웠습니다.

웹에도 세션 서비스 테스트 6개가 있었지만, 실제 라우터에서 보호 경로가 막히는지,
로그아웃 실패 후 화면과 캐시가 유지되는지, 조회 재시도로 화면이 복구되는지는 별도 검증이
필요했습니다. 전체 소스를 기준으로 측정하는 커버리지도 없었습니다.

이번 작업의 목표는 기존 회귀 검증을 유지하면서 HTTP·화면 테스트와 측정용 리포트를
추가하는 것이었습니다. 새 제품 기능, DB 스키마 변경과 운영 배포는 범위에 넣지 않았습니다.

## A — Analysis

### 1. 객체를 직접 만드는 테스트는 Nest의 생성 경로를 검증하지 못했습니다

기존 AuthGuard 단위 테스트는 `new AuthGuard(auth)`로 의존성을 직접 전달했습니다.
이 테스트가 통과해도 `@UseGuards(AuthGuard)`를 처리하는 Nest의 생성 경로가 같은 방식으로
동작한다는 보장은 없었습니다.

실제 AuthModule을 사용하는 HTTP 테스트에서 API 테스트 283개 중 279개가 통과하고
4개가 실패했습니다. 실패한 테스트는 정상 인증의 200 또는 잘못된 인증의 401을 기대했지만
500을 받았습니다. 공통 원인은 AuthGuard에서 AuthService가 주입되지 않아
`authenticate`를 호출할 수 없다는 것이었습니다.

AuthModule에는 가드를 만드는 factory provider가 있었지만, Nest의 가드 처리 경로는
모듈의 injectables에서 가드 인스턴스를 찾습니다. 생성자의 명시적 주입 정보가 없는
AuthGuard는 이 경로에서 AuthService를 받지 못했습니다. 테스트에서 가드를 대체하면
이 오류를 다시 놓치므로, 실제 가드를 유지한 상태에서 주입 정보를 보완해야 했습니다.

### 2. 러너 이관에는 모듈 형식과 객체 실행 환경의 차이가 있었습니다

API는 TypeScript의 Nest 데코레이터 변환과 메타데이터가 필요해 Jest + ts-jest의 CJS
환경을 선택했습니다. 설치된 `@nestjs/jwt` 12는 ESM으로 배포되어, 해당 의존성의
JavaScript만 테스트에서 CJS로 변환하도록 설정했습니다.

TypeScript가 상대 `.ts` import를 `.js`로 재작성하는 설정도 유지했습니다. 테스트 전용
resolver는 실제 `.js`를 먼저 찾고, 없을 때만 `.ts`로 해석합니다. 실제 JavaScript의
우선순위와 누락된 소스의 오류 보존을 별도 테스트로 확인했습니다.

Jest와 Node의 실행 환경에서 만들어진 배열은 내용이 같아도 엄격한 비교에서 실패할 수
있었습니다. 해당 응답 배열을 테스트 환경의 배열로 펼쳐 기존 내용 검증을 유지했습니다.
예상 밖 예외의 재전파 테스트는 전달한 예외 객체가 그대로 돌아오는지 확인하도록 바꿨습니다.
기존 시나리오와 `node:assert` 검증을 유지하면서 이관에 필요한 표현을 조정했습니다.

### 3. 커버리지에는 실행 범위와 검증 한계를 함께 남겨야 했습니다

기본 테스트가 운영 설정 파일을 읽으면 실제 DB·AWS에 접근할 가능성이 생깁니다.
API 테스트에서는 운영 환경 로더를 대체하고, Prisma·AWS·Instagram 의존성에 가짜 객체를
사용하도록 구성했습니다. 실제 DB 테스트는 `TEST_DATABASE_URL`을 명시한 별도 명령으로
분리하고, 데이터 정리와 연결 종료를 보장했습니다.

커버리지는 각 패키지의 전체 `src`를 측정하도록 정했습니다. 기본 테스트에서 실행하지
않는 진입점과 DB 연결 코드도 측정 대상에 남겨, 검증 범위를 숫자에서 확인할 수 있게 했습니다.

## A — Action

1. API를 Jest 30.5.2 + ts-jest 29.4.14로 이관하고, Nest core와 같은 버전인
   `@nestjs/testing` 11.2.7 및 Supertest로 인증 HTTP 테스트를 추가했습니다.
2. 웹과 공유 패키지를 Vitest 5.0.3으로 이관하고 V8 커버리지 패키지도 같은 버전으로
   고정했습니다. 웹 서비스 테스트는 Node, 화면 테스트는 jsdom에서 실행합니다.
3. 웹 화면마다 새 QueryClient·MemoryRouter·Emotion ThemeProvider를 제공하고 fetch
   경계에서 응답을 대체했습니다. 로딩, 보호 경로, 조회 재시도, 로그아웃 성공·실패·재시도,
   세션 갱신·401 만료와 위조된 연결 성공 URL을 검증했습니다. 기존 늦은 응답·캐시 제거
   테스트도 유지했습니다.
4. HTTP 테스트가 발견한 AuthGuard 생성자에 `@Inject(AuthService)`를 추가했습니다.
   변경은 import와 생성자 주입 정보 2줄이며, 인증 정책과 응답 형식은 유지했습니다.
5. 패키지별 `test`, `test:watch`, `test:coverage`를 제공하고 `pnpm verify`를
   타입 검사 → 커버리지 테스트 → 빌드 순서로 바꿨습니다. 테스트·설정 파일도 타입 검사합니다.
6. 테스트 도구와 커버리지 정책을 [ADR 0004](../docs/adr/0004-test-runners-and-coverage.md)에
   기록하고 개발 문서와 AGENTS 규칙을 갱신했습니다.

**안 만든 것**: 최소 커버리지 통과율과 신규 CI는 추가하지 않았습니다. 이번 수치는
검증이 부족한 곳을 찾기 위한 첫 기준이므로, 수치를 맞추기 위한 테스트를 요구하지
않기로 했습니다. 실제 DB 테스트와 실계정 OAuth 브라우저 검증도 실행하지 않았습니다.
운영 배포·커밋·푸시는 수행하지 않았습니다.

## R — Result

Node.js 24.21.0과 pnpm 10.5.2에서 최종 검증을 실행했습니다. HTTP 테스트는 실행 환경의
로컬 포트 제한(`EPERM`)을 확인한 뒤, 로컬 서버를 열 수 있는 허용된 환경에서 검증했습니다.

| 명령 | 최종 결과 |
|---|---|
| `pnpm verify` | 세 패키지 타입 검사, 전체 커버리지 테스트, API·웹 빌드 통과 |
| `pnpm test` | API 283개 + 웹 21개 + 공유 1개, 총 305개 통과 |
| `pnpm -F @ig/api build:lambda` | HTTP·SQS Lambda 번들 생성 통과 |

AuthGuard 수정 전 API는 279개 통과·4개 실패였고, 수정 후에는 283개가 모두 통과했습니다.
커버리지 실행과 일반 테스트 실행 모두 같은 결과를 확인했습니다.

아래 수치는 최종 통과 실행의 JSON 요약입니다.

| 패키지 | 구문 | 분기 | 함수 | 줄 | 측정 소스 파일 |
|---|---:|---:|---:|---:|---:|
| API | 88.00% | 87.04% | 88.88% | 88.00% | 42 |
| 웹 | 69.27% | 58.27% | 48.75% | 69.64% | 15 |
| 공유 | 100% | 100% | 100% | 100% | 1 |

공유 패키지의 분기는 측정 대상이 0개이므로 100%는 분기 시나리오의 충분성을 뜻하지 않습니다.
러너별 집계 방식이 다른 패키지 수치를 하나의 평균으로 합치지 않았습니다.

총 58개 소스 파일에 측정 누락이 없고 테스트·지원 코드·타입 선언·Prisma 생성 코드가
포함되지 않았음을 파일 목록과 대조했습니다. 세 패키지 모두 `coverage/`에 HTML,
LCOV, JSON 요약을 생성했으며 산출물은 Git에서 제외합니다.

`TEST_DATABASE_URL`이 없는 DB 테스트 명령은 연결 전에 실패하는 것을 확인했습니다.
실제 PostgreSQL의 동시성, 운영 Lambda 실행과 실계정 OAuth는 이번 통과 결과가 보장하는
범위에 포함되지 않습니다. 웹의 가입 요청·온보딩 처리와 API 진입점 등 낮은 커버리지 영역도
후속 검증 대상으로 남아 있습니다.

이번에 바뀐 판단은 테스트 수나 커버리지만으로 앱의 연결 상태를 판단하면 안 된다는 것입니다.
단위 테스트는 처리 로직을 검증하고, 실제 프레임워크를 사용하는 테스트는 그 로직에 필요한
의존성이 올바르게 연결되는지도 검증했습니다.

## 면접용 30초 요약

> Instagram 자동 DM 서비스의 기존 테스트를 Jest·Vitest로 이관하고 인증 HTTP·화면 테스트를
> 추가했습니다. 실제 Nest 앱으로 검증하자 단위 테스트가 놓친 AuthGuard 주입 누락 때문에
> 인증 요청이 500을 반환하는 오류를 발견했습니다. 가드를 테스트에서 대체하지 않고
> 생성자에 명시적 주입 정보를 추가해 해결했습니다. 최종 305개 테스트, 전체 빌드와 Lambda
> 번들이 통과했고, 전체 소스 58개를 대상으로 패키지별 커버리지를 측정했습니다. 운영 환경과
> 실제 DB는 테스트에서 분리했으며 커버리지는 개선 기준으로 사용하고 최소 통과율은 두지 않았습니다.
