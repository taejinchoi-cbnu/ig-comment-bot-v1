# OAuth 전에 가입 요청의 상태와 웹의 가장 얇은 경로를 먼저 만들었다

> 2026-09-20 · Phase 2 기반 구현
>
> Phase 1은 API·SQS·DB를 직접 다뤄야만 쓸 수 있었습니다. OAuth를 바로 붙이기 전에,
> 사용자가 어디서 기다리고 운영자가 무엇을 처리하는지부터 코드의 상태로 만들었습니다.

## P — Problem

Phase 2의 목표는 지인이 설명 없이 자동 DM을 설정하게 하는 것입니다. 하지만 새 사용자의
첫 행동, 운영자의 테스터 초대, 초대 수락 뒤 OAuth 시작을 연결하는 데이터 모델과 화면이
없었습니다. OAuth callback만 먼저 만들면 어느 가입 요청의 결과인지, 사용자는 초대를
기다리는 동안 무엇을 봐야 하는지, 운영자는 어디서 다음 단계로 넘기는지 정해지지 않습니다.

기존 인증은 이메일·비밀번호와 Bearer JWT를 전제로 했습니다. OAuth는 이메일을 주지 않으므로
최종 사용자 가입의 답이 될 수 없지만, 운영·복구 API에 인증 경계 자체가 없는 상태도 유지할
수 없었습니다.

## A — Analysis

사용자에게 새 개념을 늘리지 않는다는 제품 원칙을 적용하면, 첫 입력은 Instagram username
하나면 충분합니다. 토큰·app secret·webhook URL을 물으면 Phase 1의 운영 절차를 그대로
사용자에게 넘기는 셈입니다.

다만 "초대를 보냈다"는 Meta의 역할 상태와 서비스의 화면 상태는 다릅니다. OAuth 처리 상태와
계정 연결 상태까지 한 boolean으로 표현하면 재시도와 오류 화면의 의미가 섞입니다. 그래서
가입 요청은 독립 행으로 두고 아래 상태를 가졌습니다.

| 상태 | 뜻 |
|---|---|
| `REQUESTED` | 사용자가 username을 남겼고 운영자 초대 전입니다. |
| `INVITED` | 운영자가 Instagram Tester 초대를 보냈습니다. |
| `AUTHORIZING` | 다음 OAuth callback이 처리할 상태입니다. |
| `CONNECTED` | OAuth·계정 저장·구독 확인까지 성공했을 때 쓸 상태입니다. |
| `ERROR` | OAuth 구현에서 사람이 읽을 수 있는 실패 상태로 사용할 예정입니다. |

웹과 API가 같은 상태 이름을 따로 복사하면 연결 화면이 서버와 어긋날 수 있습니다. 현재는
`packages/shared`를 웹의 username 검증·온보딩 DTO에 사용하고, API는 자체 입력 정규화와 반환
타입을 유지합니다. 따라서 양쪽이 같은 패키지를 공유한다고 기록하면 안 되며, OAuth 구현 때
상태 정의를 한 곳으로 합칠지는 별도 결정으로 남깁니다.

비밀번호 해시는 Lambda arm64 번들에서 네이티브 바이너리를 따로 관리해야 하는 Argon2 패키지
대신 WASM `hash-wasm`의 Argon2id를 사용했습니다. JWT 서명키도 새 평문 환경변수를 만들지
않고, 기존 마스터 키에서 HKDF로 용도 분리해 파생했습니다. 이 경로는 최종 OAuth 로그인과
경쟁하는 기능이 아니라 운영·복구용 기존 인증 경계를 보존하기 위한 것입니다.

## A — Action

1. `OnboardingRequest`와 상태 enum·색인을 추가하고, username 정규화 후 `REQUESTED`를 만드는
   API와 요청 상태 조회 API를 만들었습니다. 반환 DTO에는 본문·토큰·시크릿을 넣지 않습니다.
2. 운영자가 Meta 대시보드에서 실제 Tester 초대를 보낸 뒤 요청을 `INVITED`로 바꿀 수 있는
   명령을 추가했습니다. 별도 관리자 화면은 만들지 않았습니다.
3. React/Vite·공유 패키지·모바일 우선 UI를 세팅하고, 가입 요청 화면과 10초 polling 초대 대기
   화면을 구현했습니다. 초대 수락 화면은 새 창으로 열고, 연결 버튼은 다음 OAuth 작업의
   endpoint 자리를 가리키게 했습니다.
4. 운영·복구용 이메일 가입·로그인·`GET /api/auth/me` Bearer 경로를 추가했습니다. 가입자는
   `PENDING`으로 만들고 운영자가 `ACTIVE`로 바꾼 경우에만 로그인할 수 있게 했습니다.
5. 연결 뒤를 가정한 대시보드 자리와 "첫 자동 DM" 행동만 두었습니다. 게시글 조회·자동 DM
   저장·활동 피드는 아직 넣지 않았습니다.

**안 만든 것**: OAuth callback, HttpOnly 브라우저 세션, Instagram ID 사용자 연결, 토큰 저장,
webhook 구독은 이 단계에서 구현하지 않았습니다. 화면이 있어도 연결이 실제로 끝나는 척하면
안 되므로, 이 경계는 다음 OAuth 작업으로 남겼습니다.

## R — Result

사용자 흐름은 이제 다음처럼 상태가 보이는 형태가 됐습니다.

```
Instagram username 입력 → REQUESTED 대기 화면
운영자 Tester 초대 + INVITED 전환 → 초대 수락 안내
수락했어요 · 연결하기 → 다음 OAuth 시작 endpoint
```

가입 요청은 username만 저장하며, 브라우저 `localStorage`에는 그 요청을 다시 찾기 위한
불투명 ID만 둡니다. access token과 Instagram 비밀번호를 저장하거나 입력하는 화면은 없습니다.

인증과 온보딩 서비스에는 각각 입력 정규화, 중복·미승인 로그인 거절, Bearer 형식, 존재하지
않는 요청 거절, 시크릿 미노출을 보는 단위 테스트를 붙였습니다. 이 단계의 결과는 OAuth 완성이
아니라, 다음 구현이 연결할 수 있는 상태 전이와 사용자 화면의 뼈대입니다.

## 남은 것

- OAuth 시작·callback에서 요청 상태를 `AUTHORIZING`, `CONNECTED`, `ERROR`로 실제 전이
- `state` 검증, 60일 토큰 교환, `/me` 계정 확인, 암호화 저장, webhook 구독 재조회
- Instagram ID 기반 사용자와 HttpOnly 세션 쿠키 연결
- 현재 이메일·비밀번호 필수 `User` 모델을 OAuth 사용자도 수용하도록 전환

이 항목들은 [`2026-09-20-oauth-onboarding-before-implementation.md`](./2026-09-20-oauth-onboarding-before-implementation.md)의
사전 설계 범위입니다. 아직 구현 결과로 기록하지 않습니다.

## 배운 것

### 1. OAuth는 로그인 버튼이 아니라 상태 전이의 마지막 단계다

OAuth callback을 만들기 전에 가입 요청의 소유자와 초대 대기 상태를 만들자, callback이
어느 행을 성공·실패로 바꿔야 하는지가 명확해졌습니다. 외부 인증은 화면 하나가 아니라
사용자·운영자·외부 플랫폼을 잇는 긴 작업의 한 단계였습니다.

### 2. 최종 사용자 경로와 운영 복구 경로는 같은 인증 수단일 필요가 없다

이메일/Bearer JWT는 OAuth가 완성되면 주 사용자 흐름에서 숨겨져야 합니다. 그렇다고 운영자가
계정 상태를 복구하거나 API를 점검할 인증 경계까지 없앨 이유는 없습니다. 같은 `User`를
공유하되, 어떤 경로가 누구를 위한 것인지는 구분해야 했습니다.

## 면접용 30초 요약

> Instagram OAuth를 바로 붙이지 않고, 먼저 가입 요청과 테스터 초대의 상태를 독립 모델로
> 만들었습니다. 사용자는 username 하나만 입력하고, 운영자가 Tester 초대를 보낸 뒤 화면은
> `REQUESTED → INVITED` 상태를 polling으로 보여줍니다. OAuth는 그 뒤의 `AUTHORIZING →
> CONNECTED/ERROR`를 책임지게 할 예정입니다. 웹은 공유 패키지로 입력과 DTO를 관리하고 API는
> 현재 독립적으로 검증합니다. 운영·복구용 인증은 Lambda 호환 WASM Argon2id와 HKDF로 파생한 JWT 키를 써서
> 별도 평문 시크릿을 늘리지 않았습니다. 이 기반 덕분에 다음 OAuth 작업은 버튼을 만드는 대신
> 기존 가입 요청을 안전하게 연결하는 문제로 좁아졌습니다.
